  **Why this frame does not fully meet its checklist** ("at most a few chunks still loading at the far edge, near terrain fully present"): the gaps are in the middle distance, not only at the far edge, and they are not a few chunks. The cause is the streaming speed on SwiftShader, from the M04a notes: one section upload costs 6–10 ms (`uploadMsP95` was 5.2–10.8 ms across ten flights), so a frame can upload about one section; the GPU runs at about 1.3 frames per second at RD 8 (0.4–0.8 s per frame); and drawing ~740 sections costs about 5 ms. Streaming cannot keep up with a 30 blocks/s flight here, so the frame shows the streaming state. The orchestrator decided to keep it as a known limitation for this PR. **M22a is asked to retake this frame** once draw submission and upload cost are lower.

## Heap baseline (review round 1, B1)

**Root cause.** At spawn the heap held about 7.7 MiB more `system / JSArrayBufferData` than after a flight, and the drop was all in 4,096-byte buffers (`system / JSArrayBufferData`: 2,016 at spawn, 2 after; from a heap snapshot at spawn and after one out-and-back, probe run, both after two GCs). The page reports the same thing directly: `LightStorage` holds **2,014 light sections (8,249,344 B) at spawn and 0 after the flight**. Each light section is one `Uint8Array(4096)` (`src/world/lighting.ts`). `createWorld` computes that light for the spawn region (the barrier columns, radius 5). The light is kept while those columns are loaded. The streamer frees a column's data when it leaves the keep ring, and a column streamed back in gets no light until M05b lights streamed columns.

**Why this is not a leak, and why it is not freed.** The light is needed while the spawn columns are loaded: re-meshes and edits read it. Freeing it at spawn would change what a re-mesh reads, so it is not freed. The baseline is taken after a warm-up instead: 400 blocks out and back takes the spawn columns out of the keep ring, so the baseline is taken in the state every later return to spawn reaches. (Option 3 of review round 1.)

**Effect.** Before the warm-up, the final verify run on `53d5a5f` (the merged tree, before this change) had a baseline at spawn of 18,863,296 B (17.99 MiB) and an end after the flight of 11,286,819 B (10.76 MiB): growth −40.17 %, a drop the one-sided bound cannot see. The three runs on the same tree before it had baselines of 18,854,792–18,863,296 B and ends of 11,126,863–11,270,959 B (growth −40.23 % to −41.01 %). After the warm-up the baseline is 10,845,137 B (10.34 MiB) and growth is +4.12 % (final run). The self-check (the 8,000,000-number probe) is unchanged and still passes.

**Second out-and-back (report only; separate probe run on this tree, not the test).** Baseline after the warm-up 10,820,821 B; after round 1 11,314,949 B (+4.57 %); after round 2 11,865,217 B (+9.65 % against the baseline). Round 2 is **+4.86 % above round 1**, so it does not return within 1 % of the first post-GC reading. The round-2 rise is about 0.5 MiB. The reviewer's probe measured +2.18 % for round 2, not +4.86 %. The likely cause is the frame-stats sample arrays (`src/engine/frame-stats.ts`, `MAX_SAMPLES` 100,000), which fill during the test because the heap test never calls `resetFrameStats` (only the M04a flight test does). That is unconfirmed. The growth is capped, so it plateaus rather than leaking. The one-round test is inside the bound.

**Three m04 spec runs (separate runs, same tree, before the final verify):** each run's baseline / end / growth: 10,814,525 B (10.31 MiB) / 11,325,196 B (10.80 MiB) / +4.72 %; 10,829,177 B (10.33 MiB) / 11,311,036 B (10.79 MiB) / +4.45 %; 10,835,737 B (10.33 MiB) / 11,307,664 B (10.78 MiB) / +4.36 %. Self-checks +64.65, +88.65, +61.17 MiB. Durations: heap test 2.0–2.1 min, RD 12 horizon 1.1–1.3 min, mid-flight screenshot 47.5–48.5 s, and the M04a flight 1.5 min. All inside the 180 s limit.

## What was built

- **`src/render/dither.ts`** — the 4×4 Bayer table; the same table feeds the fragment shader (`bayerGlsl()`).
- **`src/render/column-fade.ts`** — `FADE_IN_MS = 400`, `fadeAmount`, `fadeStartFor` (the full-opacity rule), `UniformValueCache` (writes a uniform only when its value changes), `ColumnFades` (a fade starts at the first section upload of a column with no section meshes on the GPU, and ends when its last section mesh is freed).
- **`src/render/chunk-renderer.ts`** — `u_fade` uniform and the dither discard at the top of the fragment shader (before the wireframe early return); the fade value is cached per column and forgotten at the start of each frame; `uploadSectionMesh(…, fadeFromMs)`; the wireframe overlay loops over visible columns so it follows the fades; `fadingColumns(nowMs)`.
- **`src/world/mesh-attempts.ts`** — `MeshAttempts`, the store of each open attempt's uploaded sections. An entry exists only while an attempt is open.
- **`src/world/streamer.ts`** — `StreamerHost.abandonMeshAttempt(cx, cz)`, called from `discardAttempt` when the column is `meshing`; `requestPending` getter.
- **`src/world/world-manager.ts`** — the streamer host uses `MeshAttempts`; abandon on `freeMesh` and `freeData`; the store is cleared with the GPU meshes in `loadInitialWorld` and `resetWorldToEmpty`; `uploadSection` passes `fadeStartFor(this.loadPending, now)`; `getStreamingStats()` returns `WorldStreamingStats` (adds `columnsFading`).
- **`src/debug/api/core.ts`, `src/debug/api/streaming.ts`** — type updates only.
- **`tests/e2e/helpers/sky-holes.ts`** — `isSkyPixel`, `findSkyHoles` (flood fill from the top row, then the largest 4-connected enclosed component), `MAX_HOLE_PIXELS = 64`.
- **`tests/e2e/m04.spec.ts`** — the three M04b tests, the heap warm-up and self-check, the pre-shot coverage and fade checks, and the hole check.

## Known limitations

- **Light data is lost on return to the spawn region.** Streamed-back columns are not lit until M05b, so the lit spawn state is not reproduced after a flight. This is the reason the heap baseline changes between spawn and after a flight, and it is a lighting gap, not a memory bug.
- **Per-round growth is not explained (unconfirmed).** One out-and-back is +4.12 % in the final run. In my probe the second round was +4.86 % above the first (about 0.5 MiB); the reviewer's probe measured +2.18 %. The likely cause is the frame-stats sample arrays (`src/engine/frame-stats.ts`, `MAX_SAMPLES` 100,000), which fill during the test because the heap test never calls `resetFrameStats`. The growth is capped, so it plateaus rather than leaking. The 15 % bound is one-sided, so a drop is not checked.
- **The heap test's margin to its 180 s timeout is thin.** It takes 2.0–2.1 min alone. The reviewer measured 3.9 min for the warm-up plus two rounds with heap snapshots. The timeout is not changed here.
- **The hole check does not catch a column at the RD edge.** Its sky is open (it reaches the top row, or the frame edge past it), so it is reported as open sky, not as a hole. It catches missing interior chunks.
- **The hole seed is the top row only.** As specified and kept by the orchestrator's decision. On the fast-flight frame the top row is terrain, so all sky there is enclosed (39,515 px). The frame cannot say whether that is terrain not yet drawn or sky beyond the RD 8 edge: a separate probe at the same pose measured 0.60 % sky after streaming went idle at RD 8 and 0.07 % at RD 12, so part of it is beyond the RD 8 edge.
- **Fast-flight frame does not meet its checklist** (see Screenshots). Kept as a known limitation for this PR; M22a to retake.
- **The fade is rarely seen under SwiftShader.** A frame takes about 0.75 s here, so a 400 ms fade usually ends before the next frame. The dither is visible at the edges of the sky patches in the fast-flight frame. No e2e test checks a pixel mid-fade; the dither itself is covered by unit tests of the table.
- **A column whose generation failed three times still blocks its neighbours** (the known M04a limitation). No test here hit it.
- **Mesh failures are still silent** (M04a limitation).
- **A column whose meshes are all freed by a stale completion fades again** when it comes back: `finishIfDone`'s stale branch frees the column's meshes, so the column disappears and fades back in. That is outside decision 2 as written and is not changed here.

## Notes for dependent tasks

- **M05b** (lighting): streamed columns are not lit, so the lit spawn region and a streamed-back column differ in memory and in look. Lighting streamed columns will raise the memory of a streamed-back state; the heap test's warm-up baseline will then need to be re-checked.
- **M22a** (culling and batching): retake `m04-fast-flight.png` once streaming keeps up at RD 8 (the frame in this PR is a known limitation). `ChunkRenderer.render()` sets `u_fade` per column in each pass; a batched draw must keep the fade per column (one uniform per column, or per batch of columns with equal fade).
- **Debug API:** `getStreamingStats()` returns `WorldStreamingStats`; `columnsFading` is time-based, read at the call. A test that waits for it to reach zero should still wait two frames before a screenshot.
- **Attempts:** `StreamerHost.abandonMeshAttempt` must be implemented by any new host; the streamer calls it from `discardAttempt` only while a column is `meshing`.
- **Heap test:** `window.gc` needs `--js-flags=--expose-gc`, and the readings need `--enable-precise-memory-info`; both are in `playwright.config.ts`. The test throws if `window.gc` is missing. The probe checks that the reading responds to a known allocation before the flight. The baseline is after a 400-block warm-up.
