## What was built

- **`src/world/streaming-plan.ts`** — the pure rules: render distance clamp (2–32), rings (generate RD+1, mesh RD, keep meshes RD+1, keep data RD+2), Chebyshev distance, ring offsets, the smoothed travel direction (`TravelTracker`), the priority key (ring, in-frustum, travel dot product, distance), `neighboursReady`, `canFreeData`.
- **`src/world/streamer.ts`** — the one owner of column state (`queuedGen / generating / generated / queuedMesh / meshing / meshed`). Works against a host interface so it is unit-tested with a fake host. Contains the planner (at most once per frame, when the camera column or the view changed), stale-job cancellation (counted), serials and tokens so late results are ignored, the deferred-upload queue, region requests with pins, hysteresis, and the pump (a timer task that does work between frames in slices of about 3 ms).
- **`src/world/world-manager.ts`** — `createWorld` keeps its barrier (generate and light radius 5, mesh radius 4, no terrain drawn while loading) and then lets the streamer fill up to RD; `waitForTerrain(r)` is a region request (`Streamer.moveTo` first, because with `requestAnimationFrame` held no frame tells the streamer where the camera is); `render()` runs `streamer.update`, then uploads for 3 ms; `setRenderDistance`, `getStreamingStats`.
- **`src/render/frustum.ts`, `src/render/chunk-renderer.ts`** — column-level frustum culling (conservative column AABB against the six planes, margin 0.01 block), the same function for the draw and for the in-frustum priority.
- **`src/render/fenced-error-drain.ts`, `src/main.ts`** — WebGL error drain without a blocking round trip (see decisions).
- **`src/engine/frame-stats.ts`, `src/debug/api/streaming.ts`** — `setRenderDistance`, `getStreamingStats`, `resetFrameStats`, `getFrameStats` (`frameCpuMsP95/Max`, `uploadMsP95/Max`, `glCheckMsP95/Max`, `pumpMsP95/Max`), `getGlResourceCounts`, `getRenderStats` (`chunksLoaded` = columns with block data, `chunksMeshed` = columns completely meshed, `chunksVisible` = section meshes drawn).
- **`tests/e2e/helpers/flight.ts`** — `fly()` (page-side loop, wall-clock speed, waits two frames at the end), `waitForStreamingIdle()`.

## Decisions (links to decisions/ files)

- `decisions/M04a-streaming.md` — owner decisions 1–8, column-level culling, SPEC d37918d (option A), fenced error drain and how it differs from `decisions/M01a-fix-gl-error-check.md` point 2, the upload rule, no fence-gating of uploads, SwiftShader findings, options considered.
- Added after that file was written (not yet in it, described here):
  - **Work between frames is in steps.** The handler of a worker result used to store a whole column (20 sections) or copy the padded sections of a whole column, up to 277 ms under CPU contention. `StreamerHost.applyGen` now returns steps (the column with its biome data, then one per section) and `requestMesh` returns one starter per section; the pump runs them alternately for about 3 ms per slice. A generation slot stays taken until the column is stored; a mesh slot is given back when a column is discarded before all its jobs started.
  - **Background jobs leave one mesh worker free.** `WorkerPool.enqueueMeshJob(..., background)`: streaming jobs never take the last idle worker of a pool with more than one worker, so a foreground job (an edit to re-mesh; the M02 WorkerPool test) starts at once. Without it the M02 test was flaky, because streaming now keeps meshing after `createWorld`.
  - **Flight test frame floor** is 10, not 20: the flight is 33 s of wall-clock time and SwiftShader draws 1–2 frames per second at RD 8 (16 frames in one loaded verify run).

## Known limitations

- **`uploadMsP95` and `frameCpuMsP95` are above the M22a budgets on SwiftShader** (5.2–10.8 ms and 8.6–12.3 ms in ten flights). See "Notes for M22a".
- **A 50 ms assertion on wall-clock time is exposed to CPU contention.** In plain `npm run verify` Playwright starts 2 workers on this 4-core machine, and a step that takes 0.3 ms alone (storing one section, copying one padded section) was measured at 25–131 ms when the OS preempted the renderer. Tasks were already cut to single sections for that reason (pump max fell from 277 ms to 53–58 ms under load), but a miss of a few ms remains possible there: in two plain verify runs the flight test failed on `pumpMsMax` 53.3 and 57.8 (and once earlier on 161); alone and under `CI=1` it was 11.9–20.5 ms in 11 runs. The CI workflow runs one worker.
- `glCheckMsMax` (blocking `getError` when four frames are in flight) is 1.8–2.1 s alone: it is the time the GPU needs for the frames before it (SwiftShader), counted outside `frameCpuMs` as the owner decided.
- A column's mesh jobs are started section by section, so on a loaded machine the first meshes appear a little later than when a whole column was started at once.

## Notes for dependent tasks

- **M04b** (fade-in, memory): column state is `Streamer.phaseOf(cx, cz)`; a column reaches `meshed` after its last section was uploaded (`StreamerHost.uploadSection` is the single upload place; `freeMesh` the single GPU-free place). Fade-in can start when `uploadSection` is called for a column's first section.
- **M06a** (player): `fly()` in `tests/e2e/helpers/flight.ts` is the one place that sets the camera; switch it to teleport the player. The streamer reads the camera once per frame in `WorldManager.render()` through `streamerView(camera)`; after placing the camera without frames (a test holding `requestAnimationFrame`) call `waitForTerrain`, which calls `Streamer.moveTo`.
- **M05+** (edits): call `Streamer.invalidate(cx, cz)` after changing blocks so the column is meshed again; mesh jobs for edits should be enqueued with `background = false` so they use the reserved worker.
- Invariant (unit-tested after every step): a column with a mesh, or whose mesh jobs are running, has all eight neighbour columns loaded. Data is freed only when no neighbour holds a mesh (`canFreeData`).
- `getStreamingStats()` fields: `renderDistance, genQueued, genRunning, meshQueued, meshRunning, uploadsDeferred, cancelledJobs`.

## Notes for M22a (what limits p95 in this environment)

- **One section upload costs 6–10 ms on SwiftShader** (`bufferData` of the section's vertex and index data, plus the VAO setup). The frame always uploads at least one section, so `uploadMsP95` is the cost of one section upload, above the 3 ms budget. To get under 3 ms the upload unit must be smaller than a section (one bucket per call, or sub-allocation from a big buffer with `bufferSubData`).
- **Draw submission of about 740 visible sections costs about 5 ms** (3 GL calls per section). Section-level culling and batching (merged buffers, multi-draw) are what lower it; column-level culling already keeps it to the columns in view.
- **The GPU runs at about 1.3 frames per second at RD 8** (0.4–0.8 s per frame). `gl.getError` and `bufferData` block the main thread while the GPU is behind (the reason for the fenced drain and for the rule that uploads happen only inside the frame budget).
- **Fence status becomes visible about 20 frames late** in Chrome (sampled at each frame start, 18–24 fences reported unsignalled while a blocking `getError` showed a backlog of about two frames), so uploads cannot be gated on "the GPU has caught up": with that gate 269 uploads stayed deferred for 120 s. Not done; see the decisions file.
- Cost to expect from M22a work on this machine: the budget of 8 ms `frameCpuMsP95` at RD 8 needs the draw submission and the upload unit to shrink together.
