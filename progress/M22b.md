## What was built

- Local Overworlds above RD12 can retain full voxel terrain through 12 chunks and render seed-derived, textured voxel terrain beyond it. Workers build flat tops and exposed vertical sides in 1-, 2- and 4-block cells through RD16, RD24 and the remaining distance. Each tile chooses its cell size from the nearest column with hysteresis at the boundaries. Tile-edge skirts and the drawn-column mask cover transitions.
- The existing padded atlas supplies repeating surface textures and biome tint. Translucent LOD water shares voxel-water animation, depth absorption, lighting and fog, and draws over the opaque seabed.
- **Distant terrain (LOD)** is a persisted Video-tab toggle that defaults off, including for older settings. It changes streaming live and releases tile workers and GPU objects when disabled.
- GPU setup advances one step per frame within the existing timed upload path. Shader setup polls a terrain frame fence with a zero timeout, and supported drivers also use `KHR_parallel_shader_compile` to poll the link. Texture storage and each fenced unpack buffer get their own step. Tile transfers start after setup. Local world creation and loading share the existing initial-load wait and draw the pixel-art progress panel.

## Known limitations

- The seed-derived tiles omit trees, structures, cave openings and player edits. Larger cells approximate coastlines, biome edges and seabed depth.
- LOD is available in local Overworlds only, above RD12 and with the Video toggle enabled. Hollowdeep and multiplayer keep full voxels. Multiplayer join keeps its existing loading flow.
- WebGL resource calls are indivisible. Drivers without the parallel compile extension can block on an individual compile or link step.

## Notes for dependent tasks

- `src/render/lod-renderer.ts` owns staging and the shared integer quad store. Initialization, its frame fence and tile transfers all count toward the shared 3 ms upload budget and are reported in `uploadMs`. The full-detail mask follows columns actually drawn. Opaque LOD draws before the water pass, and the translucent LOD water shares the captured opaque depth.
- `setSetting('lod', true)` enables LOD in debug tests. The RD12 culling key includes FOV and aspect. The initial-load callback remains tied to the existing ready-column barrier.

### RD32 upload measurements

Same container, bundled Chromium with SwiftShader. Each run settled voxel streaming at RD12, switched to RD32 and enabled LOD in the same callback, then sampled the first 12 frames and the full startup through the first visible tile. The settled window sampled 12 frames after the RD32 plan finished. The benchmark split the voxel-side and LOD timings inside the frame upload path.

| Upload measurement | Before this review | Staged setup |
| --- | ---: | ---: |
| First 12 frames, LOD max | 42.7 ms (first tile within 4 frames) | 0.3 ms |
| Toggle through first tile, total upload p95 | 42.7 ms (4 frames) | 0.3 ms (131 frames) |
| Toggle through first tile, LOD max | 42.7 ms | 48.6 ms |
| Settled total upload p95 / max | 0.1 / 0.1 ms | 0.1 / 0.1 ms |
| Settled LOD max | 0.0 ms | 0.0 ms |
| Settled frame CPU p95 | 40.2 ms | 52.2 ms |

Both settled samples had 729 full-detail columns and 289 LOD tiles. The prior 37.8 ms settled outlier was in the voxel-side wall-clock interval. The original settled sample began after the completed LOD plan and had no LOD tiles to allocate or transfer. There is no finer attribution for that one event. The 42.7 ms live-enable stall in the replay was LOD setup, with 0 ms of voxel-side work on that frame.

SwiftShader did not expose `KHR_parallel_shader_compile`. Staging removed the monolithic first-ready-frame allocation, but a later native LOD setup frame still exceeded 3 ms. The strict startup maximum remains open in this container.
