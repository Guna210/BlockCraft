## Notes for dependent tasks

### M21b — server

- Import simulation modules under `src/world`, `src/gen`, `src/gameplay`, and
  `src/entity`; protocol API is `src/net/protocol/index.ts`. Existing registries
  use `import.meta.glob` and extensionless imports, so use Vite's SSR transform
  for a Node entry (for example `vite build --ssr`), rather than native Node
  loading raw TypeScript. The Node Vitest proof uses those transforms without DOM.
- Register creatures and block entities as the existing singleplayer bootstrap
  does. Supply `ParticleSink` only when visual effects are wanted; existing
  optional creature/survival particle parameters can be absent/null. BlastCharges
  takes an injected ParticleSink and feedback callback, which can be no-ops.
- Audio defaults to no-op. Client startup uses
  `setGameEventSink({ explosion: playExplosion })`; Node need not register a sink.
  Pass null to clear it in tests. The sink is module-local and synchronous.
- Create one `BinaryWriter` per serialization stream and call
  `encodeMessage(message, writer)`. Returned bytes borrow the writer buffer;
  copy before reusing it if the transport retains queued bytes. `decodeMessage`
  returns a typed result, and chunk payloads borrow the input frame.
- Check `rejectIncompatibleVersion(hello.version)` before login. A mismatch returns
  an encodable LoginReject with both version numbers. Bump PROTOCOL_VERSION for
  layout/enum meaning changes; there are no reserved or password fields.
- Reuse `src/persist/compress.ts` deflate outside the codec, pass the compressed
  bytes as ChunkData.payload, and cap inflated sizes before deserializing.
- Inventory request/result pairs carry request ids and revisions; validate legal
  actions, slot ownership, counts, and current revision on the server. Use full
  InventorySync or InventorySlot messages for authoritative snapshots/updates.

### M21c — client

- Prediction uses PlayerInput.sequence and PlayerCorrection.acknowledged; movement
  is forward/right, look is yaw/pitch in radians, and ActionFlag carries actions.
  Existing shared gameplay controllers take plain action/down data.
- Use `entityMove(id, previousPose, nextPose, message)` on the sender, and
  `applyEntityMove(pose, message)` on the receiver. Retain each recipient's last
  sent pose; changed fields use quantized i16/4096 deltas or f64 absolutes; the sender baseline is updated in place. Reuse a `createEntityMove(id)` message per recipient. Keep
  interpolation history outside the codec, apply messages in WebSocket order,
  and handle sequence-number wrap in the transport.
- EntitySpawn.name is optional player metadata; ChatSend and ChatBroadcast have
  separate directions. Client entity rendering loads Blast Charge skins itself;
  shared simulation no longer registers them.
