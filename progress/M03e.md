## The definition of "underground block" (decisions/M03e-ore-counting.md)

A block at y 5–100 inclusive, strictly below its column's surface (the highest block that is not air, water or lava), that is itself not air, water or lava. The count is ore blocks among those, per 1,000,000 of them.

**Iron's mountain band** is counted like everything else: every iron block that is an underground block counts, so the band's part at y 80–100 (in mountain columns) is inside the 800 target and nothing above y 100 is. It is small: 103 of 12,034 iron blocks (0.86 %) on the standard seed and 58 of 11,014 (0.53 %) on the alternative seed. The band itself (y 80–255 in `frost_peaks` and `stony_heights`) is reported separately: 381 iron in 662,085 underground blocks (575 per 1M) and 668 in 957,206 (698 per 1M).

## `locate('ore', id, near)`

Returns the block `[x, y, z]` nearest to `floor(near)` (smallest squared Euclidean distance; ties go to the lower y, then lower x, then lower z) that holds the ore, or null. Radius: the columns within 8 chunks (Chebyshev) of the column containing `near`, a square of 17 × 17 = 289 columns, all heights; `ORE_LOCATE_RADIUS_CHUNKS` documents it. Rings are visited outward and the search stops once no later ring can hold a closer block. A column that is loaded in the world instance is read as it is (so mined ore is not reported again); any other column is generated on the side with the default pipeline (one column generation each, see the Node timings below) and its ore positions are cached by world seed. Unknown ids, `skyshard_ore` and flat worlds return null. The unit tests check that the returned block is that ore in a freshly generated column (both seeds, two origins, all five ores), that the result equals an independent brute-force search, that it is deterministic, and that a loaded column's edit is respected. The e2e test runs it through `window.__blockcraft.locate` on the production build: the five blocks it returned near (0, 64, 0) are `coal_ore` (8, 71, −3), `copper_ore` (2, 59, −9), `iron_ore` (−8, 35, −15), `gold_ore` (4, 22, 8), `lumite_ore` (−30, 26, 12), and `getBlock` reports each one as that ore.

## Known limitations

- **M03c's unit test 10 rewrites committed files on every unit run.** `tests/unit/biomes.test.ts` writes `docs/screenshots/M03c/m03c-biome-map.png` and `m03c-grass-tint-map.png` each time the unit suite runs, so after any run they differ from the committed copies. This task did not commit them (the two files were restored to the committed versions before committing); the owner may want to schedule a fix (write them to `artifacts/` and copy only on purpose, or regenerate and commit them).
- Lumite's exposure bonus examines only the six neighbours inside the block's own column, so a halo cell on a chunk edge cannot see air across the border; the shares above are measured the same way and are slightly below the true ones.
- Iron's mountain band is sparse near its bottom: 0.5–0.9 % of counted iron lies at y 80–100. Appendix A.4 gives no peak for the band; 120 was chosen (see the decision).
- No Slate (deep stone) exists yet, so ores replace plain `stone` at every depth; when a deep-stone block is added, `generateOres` must accept it as a replaceable block.
- `locate('ore', …)` generates uncached columns on the main thread, one column generation each, up to 289 columns when nothing is found. It is a debug API; M04a's worker work does not change it.
- Ore is placed from the stone and the surface left by the earlier stages; a later task that changes either must keep `tests/unit/ores.test.ts` placement test "c" passing.
- Lumite at 12 emits block light; the light engine already reads `lightEmission`, and no test of this task checks lit caves (M05b owns lighting).
