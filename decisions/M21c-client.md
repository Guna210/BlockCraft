# M21c — Client networking decisions

## Loading and lifecycle

Browser transport and session code live in `src/game/net/`, dynamically imported only on connection. Shared protocol and simulation stay browser-free. No networking fields were added to World or Player, and single-player receives no network tick/frame hook. Player checkpoint methods are called only by prediction.

Connection retains ServerHello and all subsequent messages until the game subscribes, then preserves wire order. An asynchronous receive chain also orders column decompression. Every ServerHello replaces the presentation world, including portal travel: old jobs, meshes, entities, labels and prediction history are cleared. Outgoing input sequences and the cumulative correction counter continue across travel. The server clears recipient entity baselines so destination entities receive fresh spawns.

A remote spawn creates only a Player. Its world never advances local AI, spawning, block ticks, fluids or portal mechanics. No save session is attached; generation requests resolve exclusively from received columns. Main-thread generation is explicitly rejected in remote mode. Quit restores controller, renderer and input callbacks, removes overlays/timers and permits ordinary single-player startup afterward.

## Terrain and presentation

ChunkData uses `deserializeColumn`; decoded biome indices are rebound to the dimension's biome table, including the Hollowdeep fix. Columns are adopted immediately, so later edits cannot be overwritten by delayed generation-style jobs. The existing lighting and meshing workers run locally. ChunkUnload releases data and GPU meshes. Replicated portal cells build rendering records without local activation, collapse or travel.

Remote entities keep independent delta baselines and preallocated 32-pose timestamp rings. Rendering samples 100 ms in the past, with linear position/pitch and shortest-arc yaw. Remote players use the existing player model. Other registered entities/items use their existing presentation components without advancing AI or physics. Poses are sampled before rendering; labels project that same pose after the camera update. Name tags use textContent, the shared UI palette, projected head positions and transform-only frame updates; behind-camera tags move offscreen.

## Prediction and block actions

A 256-entry preallocated input ring retains sequence, intent, post-tick pose and shared Player checkpoint storage. Corrections drop acknowledged inputs, restore the authoritative movement checkpoint, replace position/velocity and replay outstanding inputs. A prediction-owned preallocated Float64Array(3) saves the visible position before correction; after replay, displacement over 0.01 blocks increments the correction counter and records a trace, including repeated acknowledgements whose input frame has already left the ring. Missing-frame traces use the available live checkpoint and message data. Live look and input state survive replay. Sequence comparisons handle u32 wrap.

Raw InputEngine states are sampled into a reused intent message. Browser connection opts into a dedicated module worker which owns the WebSocket, reusable binary writer, input sequence and 50 ms deadline clock. The worker keeps sending held intent while rendering or column decompression occupies the main thread, with six ordinary unacknowledged inputs and a seventh reserved for immediate input. It emits the exact input packet to main-thread prediction before any subsequent server message, preserving their combined order through the session's receive chain. The direct-socket Connection adapter remains available without an input worker. Both paths are dynamically loaded only for multiplayer.

Immediate input applies one preallocated provisional movement step in the next animation frame while the worker assigns its sequence. Incoming worker inputs replace that step in wire order; earlier clock inputs replay the provisional step from a separate checkpoint, and the matching immediate receipt consumes it without applying physics twice. Reconciliation includes the provisional step before measuring visible displacement, so the correction counter continues to count what the player sees. Older worker input receipts preserve a newer camera look. Before a BlockAction, changed look is flushed as a real sequenced input to preserve server ray validation. ServerHello pauses the worker input clock until the replacement world is ready while the socket stays connected. Disconnect stops sending in the worker immediately; socket close/exit terminates it.

Diagnosis used a temporary full-history trace matched against server checkpoints. Of 168 visible corrections, 138 were vertical-only, 7 horizontal-only and 23 mixed; 84 were in water, 113 in or near water, and 17 changed ground/landing state across replay. All 168 were repeated acknowledgements, with exact authoritative pose, ground, jump, sprint, yaw, pitch and movement-tick agreement; none involved a missing client column. Main-thread timer starvation triggered neutral server steps while inputs waited to be sent. Bounded main-thread catch-up still produced 119 corrections and input-rate warnings and was discarded. Independent worker transport plus provisional next-frame input produced zero corrections in the focused 30-second walk. The temporary trace cap and diagnostic logging are not retained.

Player movement is input-driven on the server. Each queued PlayerInput advances shared Player physics exactly once, and each server tick drains at most three inputs in order from the existing bounded queue. A per-peer MovementClock owns the silent-tick count without adding fields to Player or World or allocating during ticks. Ordinary ticks without input leave locomotion unchanged. Starting on the fifth consecutive silent tick, one neutral-input Player tick runs per server tick so gravity and fluid physics cannot be frozen by withholding input. Survival damage, combat, bow, block interaction, world simulation, mobs and items retain their once-per-server-tick scheduling. Reach, break timing and inventory validation are unchanged.

The authoritative per-peer MovementClock also owns a numeric step-credit budget: **burst cap 3**, initially full, replenished at one credit per 50 ms of elapsed monotonic wall-clock time. Every applied input and every neutral step spends one. The input loop checks credit before changing input state or popping the existing queue, so exhausted credit delays acknowledgement without dropping or reordering queued inputs. The pre-existing queue-full and four-received-input rate handling are unchanged. The server passes performance.now() captured at tick start; fractional credit is retained, a step requires a full credit, and credit remains capped at three. Over elapsed time E milliseconds, movement is bounded by floor(E / 50) + 3 shared physics steps. Slow setInterval ticks can drain honest 20 Hz input rather than permanently falling behind. World/portal reset clears the silence timer without refilling credits.

Silence means an empty input queue, not a credit-starved nonempty queue. Neutral steps start only after five consecutive empty ticks and share the credit budget. The client checkpoint needs no credit mirror: acknowledgements already identify the actual applied inputs, and a nonempty queue receives credit based on elapsed real time, so acknowledgement continues to advance instead of masquerading as silence. The client keeps its existing exact input/neutral reconstruction. New tests cover 600 offered inputs over 200 ticks against a bound computed by shared Player physics, ordered queue retention, zero-correction 0/2 jitter, neutral-step charging and reset preservation.

Credit-induced queueing exposed a missing checkpoint component: shared Player physics mutates health, death, hunger, saturation and exhaustion. Replaying a landing repeatedly applied damage outside the restored movement state, killing only the client and stopping prediction. A deterministic regression reproduced client health 0 versus server health 16. Slots 33–37 of the existing preallocated 48-number checkpoint now restore these existing survival fields alongside movement, so each input's effects apply once in the reconstructed timeline. No fields or tick/frame work were added to the single-player path. This is local checkpoint restoration, not a new authoritative vital-state protocol.

One PlayerCorrection remains ordered after each server tick and acknowledges only the last applied input sequence; neutral ticks never advance it. The client authoritative checkpoint applies every newly acknowledged input in order, including multiple inputs covered by one correction. The same shared MovementClock advances neutral physics after five repeated acknowledgements and performs no physics step on a plain repeated acknowledgement before that deadline. Actual server position/velocity then replace the checkpoint pose before pending input replay. The visible-snap counter is never filtered or relaxed. Clock state resets on ServerHello with the replacement presentation world.

The server's input queue has seven usable entries. Ordinary ticks keep at most six unacknowledged inputs, reserving the seventh for immediate next-frame input. Missed timer deadlines do not create catch-up bursts. This bounds queued work when generation or rendering stalls; repeated acknowledgements preserve the authoritative checkpoint unless the neutral-physics silence deadline is reached. No counter or acceptance threshold is filtered or relaxed.

BlockInteraction consumes attack/use/pick from the same sequenced input as each predicted movement step. Raw button events update worker intent and request an immediate real input, including a press/release between frames; they never advance mining while older non-attacking worker inputs are queued. This prevents local removal before StartBreak. The worker decodes only transport control packets; bulk world data is decoded once on the game path, with column decompression/adoption still ordered.

BlockInteraction predicts edits and sends StartBreak, FinishBreak, AbortBreak and Place through the real transport. Input precedes related actions; the server retains its independent ray, reach, timing and inventory checks. Authoritative BlockUpdate restores rejected predictions. Network actors clear implicit held block-interaction input, so combat intent cannot also mine/place outside BlockAction validation. Entity combat and bow input remain active. The client gates removal against elapsed time and the largest observed mining penalty during the break, matching the server's start/finish timing requirement; changing the target state or held slot aborts and restarts the break.

## Roster, inventory and UI

Protocol v3 appends PlayerList: a bounded roster of UTF-8 names and u32 ping milliseconds. Server Ping/Pong measures each peer's RTT; the server broadcasts on join, leave and every 40 ticks. The exhaustive M21a fixture map adds only the approved PlayerList fixture; its fuzz test is unchanged. Holding Tab shows the roster. Client getNetStats measures its own Ping/Pong RTT, takes playerCount from PlayerList and reports the actual correction counter.

Window-zero inventory operations are serialized through authoritative revisions. The first full snapshot sends the visible selected slot through SelectSlot, preventing a saved server selection from disagreeing with the client. Portal resets retain the client selection intent. Snapshots update the owned inventory and cursor. Predicted placement does not consume local inventory: accepted placement receives authoritative counts, while rejection may send only BlockUpdate because the server changed no counts. Deferred container/crafting windows are guarded against local mutations; M21b-fix must replace those guards as window protocols are introduced.

The existing Chat has an event-only multiplayer submit handler. ChatSend and ChatBroadcast traverse the socket; textContent renders names/text, and invisible separators, format, zero-width and bidi controls are escaped visibly. Slash commands show a short unavailable message. Disconnect or socket closure stops sending/simulation, shows the supplied reason or Connection lost, and offers a main-menu return.

Debug methods expose real remote model draws, recent BlockUpdates and the last 32 correction traces. The raw FinishBreak hook bypasses only the client reach check and still uses the server's BlockAction path.

## Test conditions and protocol limits

Networking browser tests select render distance 2 to reduce two-context SwiftShader load. No game default or acceptance threshold changes. All gameplay actions use real input/socket paths, names are unique, initial block states are checked and the 20-block target lies in received terrain. The 30-second walk jumps terrain steps and swims at the surface rather than drowning, and asserts actual travel as well as the correction budget. The shutdown test owns a separate server process and never terminates ports 3001/3002.

The existing protocol has no authoritative player vital/mode/death snapshots. Local world-survival ticks remain disabled in multiplayer. Input-derived effects inside shared Player physics are checkpointed for replay, but a later protocol extension is still needed for authoritative HUD/death states. Container windows remain expressly deferred to M21b-fix.


## Elapsed-time credit follow-up

The tick-count budget assumed setInterval ran at 20 Hz. Loaded runners can run fewer callbacks while honest clients still send at wall-clock 20 Hz, creating unnecessary acknowledgement and ordered BlockAction delay. Credit now accrues from a constructor-injected monotonic clock, with the server supplying its tick-start timestamp. The burst remains three, input/neutral costs remain one, and reset preserves both balance and accrual baseline. No client checkpoint change is needed: it still reconstructs actually acknowledged inputs and the unchanged server-tick-based neutral rule. No Player/World fields or per-tick allocations were added. Existing queue/rate guards, combat, bow, world and survival scheduling, reach and mining validation remain unchanged. Auditing server movement found only MovementClock advances player locomotion; ServerDimension.tick advances other simulation and survival once per server tick.

CI run 43379203527 shard 4 has no input queue/rate warnings in its server output. Its first-retry trace shows A reading water at the edited cell, rather than air, and a browser evaluation taking several seconds; the final attempt retained stone. Thus the evidence confirms mining/replication failure, but does not establish queue overflow as the observed cause. The clock fix independently removes the tick-rate dependency. Injected-clock tests cover honest 50 ms inputs on 75 ms server ticks with an empty queue after every drain, and malicious three-input bursts bounded by elapsed time / 50 + 3 shared Player physics steps. The prior M21c credit tests use the same injected clock; no other existing tests change.


The owner subsequently approved injecting a deterministic 50 ms-per-iteration clock into the existing M21c survival replay regression, with every assertion retained. The world replication test now chooses visible solid stone inside received terrain, reads all six neighbours with getBlock, rejects water/lava adjacency and asserts the safe neighbourhood before mining. It aims at block centres and confirms the real raycast, then uses ordinary input/socket mining. Candidate block reads precede camera look calls and real raycast confirmation. No block states are fabricated, and the air expectation, 500 ms replication limit and all other original assertions remain unchanged. This addresses the trace's water refill race while retaining elapsed-time speed validation.


## GPU submission and network responsiveness

After the fluid-safe fixture, head CI #371 still needed two world-test retries. A retained dry-stone trace returned stone after a 445.6 ms evaluation and air on the next 14.2 ms evaluation. A later local reproduction isolated the edit: the worker received it 62 ms after the sender's FinishBreak, main-thread delivery waited 2065 ms, and ordered world application took 1 ms. Both pages were visible. Fresh frame stats measured a 2018.2 ms WebGL error check while frame CPU work was 4.6 ms and streaming work below 1 ms. Synchronous error reads waiting behind queued GPU frames, rather than input credits or fluid refill, caused that deadline miss.

A frame-gating experiment kept the main thread responsive and passed an isolated replication probe in 42 ms, but waiting for GPU completion reduced model submission under two-context SwiftShader load. A form/GPU barrier also exceeded the existing 60-second Connect limit. Those one-frame/form barriers and their uncommitted helpers/tests were removed. The final approach below retains the existing four-frame budget and normal error collection.

The networking tests already selected render distance two, but their shared connect helper did so only after login: the world could begin generating/meshing/uploading at the default distance eight first. The owned world test now selects the same distance for both clients before either login. WorldManager.setRenderDistance already stores this as the next played world's distance while the panorama is active. This avoids loading an unintended larger world before measuring networking, without changing game defaults, the helper, any assertion or any timing threshold. The fluid-safe stone selection and normal network mining remain unchanged.

A preallocated 64-entry TransferTrace remains for diagnosis of block actions/updates and column delivery. Local outgoing receipts are metadata, never extra server traffic or game messages. getNetTransferTrace snapshots allocate only on request; the prediction trace and correction counter are unchanged. The world test reports frame/transfer/visibility measurements without relaxing any original assertion or timing limit. No temporary console instrumentation, lighting override or test-only game condition remains.

RemoteRenderLoop now yields only at the existing MAX_FRAMES_IN_FLIGHT bound, rather than after every GPU submission. Below the bound it submits the original frame normally. At the bound it polls a fence covering the latest submitted work; while unfinished, CPU input/prediction, entity sampling/camera/name tags and UI continue without another GPU draw or blocking error drain. Once complete, the original FencedErrorDrain reads/counts the errors and clears its frames normally. Failed polls still enter normal error reporting. No error checks or bounds are removed or relaxed. A unit test composes the real drain with the loop, exhausts all four submissions, verifies ten responsive CPU callbacks with no fifth draw, and checks completed-frame error collection and cleanup.

Entry first hands over the already-queued menu callback without creating a remote world: its next callback resolves the handover without submitting GPU commands. The latest-work fence is created afterward so that stale menu callbacks cannot bypass the bound. Reconnect handovers serialize, a cancelled connection never constructs a session, and the form checks its attempt again after asynchronous handover. Exit deletes the session fence, restores the original frame callback and resets its time baseline. The frame-loop module is dynamically imported only for multiplayer; single-player retains the original frame body without any added per-frame/tick branch or bookkeeping, and World/Player gain no fields.
