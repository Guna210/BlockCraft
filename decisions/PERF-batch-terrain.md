# PERF-batch — Terrain draw batching decisions

The owner fixed the following decisions for `PERF-batch`:

1. **Cross-column multi-draw (`src/render/chunk-renderer.ts`, `src/render/terrain-batcher.ts`)**
   - After existing column frustum, section frustum, and cave visibility culling, visible sections are bucketed into preallocated per-key lists keyed by `(pass, lightingVariant, arenaPage.id)`.
   - Opaque (`pass = 0`) and cutout (`pass = 1`) order does not matter beyond the key; each non-empty key emits `multiDrawElementsWEBGL` calls chunked only by a fixed maximum draw count per call (`MAX_MULTI_DRAW_BATCH = 4096`).
   - Translucent (`pass = 2`) retains its back-to-front sorted section order (`translucent-sort.ts`) and per-section quad sorting within `TRANSLUCENT_NEAR_DISTANCE`. Only consecutive sorted translucent sections that share `(lightingVariant, arenaPage.id)` are batched into a single `multiDrawElementsWEBGL` call (also capped by `MAX_MULTI_DRAW_BATCH`).

2. **Per-draw data texture without per-batch uniforms (`src/render/terrain-batcher.ts`, `src/render/chunk-renderer.ts`)**
   - `u_drawData[20]` is replaced by one shared 2D `RGBA32F` per-frame data texture (`u_drawDataTex`, bound on texture unit `2`, width `1024`, height `64`, capacity `32,768` draws per frame, grown if needed).
   - Each visible section draw occupies two adjacent `RGBA32F` texels at `texelBase = (u_drawBase + drawIndex) * 2`:
     - Texel 0 (`ivec2((texelBase) & 1023, (texelBase) >> 10)`): `(originX, originY, originZ, fade)`
     - Texel 1 (`ivec2((texelBase + 1) & 1023, (texelBase + 1) >> 10)`): `(tintSlot, 0, 0, 0)`
   - All draws across opaque, cutout, and translucent passes are packed into the CPU staging `Float32Array` during draw-list building and uploaded once per frame via `gl.texSubImage2D` covering only the dirty row span (`rows = ceil(totalTexels / 1024)`).
   - In the vertex shader, `int drawIdx = u_drawBase + gl_DrawID` (or `u_drawBase` when `WEBGL_multi_draw` is unavailable or disabled by `?debug=1&glcheck=draw`) reads Texel 0 and Texel 1 via `texelFetch`. `u_drawBase` is updated with one `gl.uniform1i` per multi-draw submission (or per section draw on the fallback path).

3. **Shared tint atlas texture (`src/render/tint-cache.ts`, `src/render/chunk-renderer.ts`)**
   - Per-column grass and foliage `TEXTURE_2D` bindings are replaced by `ColumnTintCache`'s shared slot-allocated 2D tint atlas (`u_tintAtlas`, `TEXTURE_2D`, bound once per frame on texture unit `1`, `RGB8`, `1024 × H`, 64 `16 × 16` cells per row), with two `16 × 16` cells per allocated column slot (`slot * 2` for grass, `slot * 2 + 1` for foliage). Using a 2D atlas instead of `TEXTURE_2D_ARRAY` avoids WebGL2's `MAX_ARRAY_TEXTURE_LAYERS = 2048` cap when 4,489 columns are loaded at RD32.
   - Slot `0` permanently holds the default plains grass and foliage tints. Loaded columns allocate integer slots from a free-list (`allocateSlot` / `freeSlot`) and upload their `16 × 16` grass and foliage cells via `gl.texSubImage2D`. When a column's last section is removed, its slot is returned to the free-list.
   - Alongside the shared 2D tint atlas, `ColumnTintCache` preserves its legacy `ColumnTintPair` handle and mock-GL fallback when `texStorage2D` is absent in unit-test mocks so existing `tests/unit/tint.test.ts` and `tests/e2e/m02c-fix.spec.ts` contracts continue to hold without modifying any existing tests.
   - Tinted output in the vertex shader (`texelFetch(u_tintAtlas, cellOrigin + tintTexel, 0).rgb`) is pixel-identical to `master`.

4. **Arena pages (`src/render/terrain-arena.ts`)**
   - Freed section ranges are placed into a per-page quarantine queue tagged with the draw frame in which they were last used. At the end of each frame that drew from an arena (`endDrawFrame` / `pollFences`), a `gl.fenceSync(gl.SYNC_GPU_COMMANDS_COMPLETE, 0)` is recorded for that draw frame.
   - Quarantined ranges are polled with `gl.clientWaitSync(fence, 0, 0)` (zero timeout, never blocking) and returned to `page.quadSpace` only after the fence inserted after their last draw frame has signalled (`ALREADY_SIGNALED` or `CONDITION_SATISFIED`). Ranges from pages never drawn are freed immediately.
   - `TerrainArena.allocate` reuses free ranges in existing pages without skipping pages drawn in the last 4 frames, because quarantined ranges already protect in-flight GPU reads.
   - `ChunkRenderer` configures page capacities starting at `1,048,576` quads (opaque, growing up to `2,097,152`), `524,288` quads (cutout, growing up to `1,048,576`), and `262,144` quads (translucent, growing up to `524,288`), keeping total arena page count across opaque, cutout, and translucent passes small at RD32 with LOD off (compared to ~2,977 pages on `master`).
   - Empty pages are released when their last active allocation is freed, preserving M04a's GPU resource return-to-baseline check and 3 ms per-frame upload deferral.

5. **Program variants and post-processing compatibility**
   - The 4 lighting program variants (`default`, `SKY_ONLY`, `WALL_TORCH`, `SKY_ONLY + WALL_TORCH`) and their lazy `#define BLOOM_EMISSIVE` variants are retained for pixel identity. Because opaque and cutout draws are grouped by variant before page, each pass switches program at most once per active variant (≤ 4 switches in opaque, ≤ 4 in cutout).
   - M22b LOD and M22c bloom `drawBuf1` / `drawBuf2` (`COLOR_ATTACHMENT1`) handling remain unchanged.

6. **Teardown and resource-count fixes (CI run 44764152550 follow-up)**
   - `ChunkRenderer.clearAllMeshes()` (the path the menu panorama, world start and Save & Quit use) now calls `TerrainArena.releaseAll()` on the opaque, cutout and translucent arenas. It drops quarantined ranges, deletes every pending fence and every page (3 buffers + 1 VAO each) without waiting on fences that will never be polled again; the next world allocates pages lazily. This returns `glBuffers` to the pre-world value (m18a-menus teardown check).
   - Pages that empty during play were already deleted once their last allocation is freed and their quarantine clears (`reclaimQuarantined` / `free`); `tests/unit/perf-batch.test.ts` now covers "emptied, then quarantined, then signalled".
   - The draw-data texture is not grown during RD8 flights (64 rows = 32,768 draws) and the tint atlas is sized for 512 slots before RD8 ever grows it. Both are created with the renderer, so they are part of the pre-world baseline; they are not deleted at teardown because `tests/unit/m08b-gpu.test.ts` requires two textures to survive `clearAllMeshes`. Growth always deletes the old texture. At teardown the draw-data buffer/texture shrinks back to 64 rows and the tint atlas to its initial slot count.
   - The extra buffer/VAO/texture counted by m04's flight were not terrain pages (page counts stayed 1/1/1 across the flight). They came from `EntityRenderer` baking each creature model's VAO, buffer and skin texture on first sight, so flying through new creature types grew the counts. With terrain batching the baseline is now small (tens instead of hundreds of resources), so a handful of lazy entity resources exceeds the ±10% window. `EntityRenderer.warmUp()` bakes every registered model once at renderer construction (called from `WorldManager` init, before the panorama's baseline), so the counts no longer depend on which creatures are met. `EntityRenderer` itself still creates models lazily so `tests/unit/m13a-render.test.ts` ("created on first use only") is unchanged.
   - Driver message "Running out of reserved outsideRenderPass queueSerial" (m04:221 flake): not reproduced locally, so page sizes and upload sizes are unchanged.
   - `EntityRenderer.warmUp()` cost, measured in this session's SwiftShader container with a temporary `performance.now()` probe (not committed): 10.8 ms for the 23 registered models, creating 23 buffers, 23 VAOs and 23 textures (GL counts 5/7/3 buffers/VAOs/textures before, 28/30/26 after). That is well under the 100 ms threshold for first terrain; it runs once at renderer construction, before any world or panorama loads. It is not test-conditional: `WorldManager` init calls it unconditionally in normal play and no test hook or flag is involved. On master the same per-model resources were already cached for the renderer's lifetime (`models` map, cleared only in `dispose()`), so only their creation time moves from first sight to init. The CI per-test first-terrain times (M02c, M22a first frame) are not separately measured here.
   - `tests/e2e/perf-batch.spec.ts` "submissions stay bounded" (this PR's own test; flaked once in CI run 44802846579, RD16 12 vs limit 11 for identical scenes). Submissions are one per non-empty `(pass, variant, page)` key plus one per 4096 draws; which pages/variants are in view depends on streaming order. The fixed "RD8 + 8" margin is replaced by a bound derived from the counted pages (`4 x (opaquePages + cutoutPages) + ceil(drawCalls / 4096)`), a page cap (RD8 opaque+cutout pages <= 4, RD16 <= 6, from the 1,048,576 / 524,288-quad initial page sizes) so the formula cannot hide page proliferation, `submissions x 50 <= drawCalls`, and RD16 `drawCalls` > 2x RD8. The existing <= 32 cap is kept.

7. **Review round 1 fixes**
   - **Idle-frame fence hole.** `TerrainArena.endDrawFrame` no longer advances `completedDrawFrame` on a frame that drew nothing while an earlier frame's fence is still pending (same for a failed `fenceSync`). Ranges freed after an unsignalled draw stay quarantined, and a page behind a pending fence is not deleted. Unit test: "an idle draw frame with a pending fence does not reclaim quarantined ranges".
   - **First-terrain cost (+~150 ms).** Breakdown from temporary `performance.now()` timers around page creation (SwiftShader container, not committed): building the shared 1,048,576-quad index pattern 29.7 ms; uploading the per-page index buffers 41.0 ms (opaque, 1,048,576 quads = 24 MB), 52.4 ms (translucent, 262,144 quads) and 29.6 ms (cutout, 524,288 quads), about 123 ms in total; `EntityRenderer.warmUp` 18.4 ms (10.8 ms in another run); tint atlas and draw-data texture creation ≈ 0.1 ms each. The vertex buffers (`bufferData(size)`) cost 0.1 ms each. So the cost was the up-front index data, not the page sizes.
   - **Fix: lazy, bounded index fill.** Pages of up to 65,536 quads still upload their full canonical index pattern at creation (<= 1.5 MB). Larger pages allocate their index storage with `bufferData(size)` and fill it with `bufferSubData` in chunks of at most 32,768 quads (768 KB) as allocations reach new offsets (`ensureIndices`, written through `COPY_WRITE_BUFFER` so no VAO state changes). The chunk is generated into one reused scratch array, so the 2,097,152-quad shared pattern (about 35 ms in one go) no longer exists and no frame builds or uploads more than one chunk per allocation. Page sizes and the owner-approved page caps (RD8 <= 4, RD16 <= 6 opaque+cutout pages) are unchanged.
   - **A/B, same container, 5 alternating runs of `createWorld` (ms, survival default world, RD8): branch 3564, 3081, 3212, 3711, 3173 (mean 3348, range 3081-3711); master c7909b1 3104, 3456, 3309, 3649, 3069 (mean 3317, range 3069-3649).** Within noise (+31 ms mean).
   - **Sorted translucent index reset is deferred.** `free()` no longer rewrites a quarantined range's sorted indices; the quarantine entry carries `restoreIndices` and the canonical pattern is written when the range is reclaimed (immediately only when it was not quarantined). Unit test: "defers resetting a sorted translucent range until its quarantine is reclaimed".
   - **Tint atlas.** `TINT_INITIAL_SLOTS` is now 512 (1024 x 256 px), matching the earlier text, so RD8 (289 columns) never grows it. The atlas never grows past `MAX_TEXTURE_SIZE` (slots <= floor(max/16) x 32); when full, further columns use the plains slot 0 and never free it. Unit test: "never grows the atlas past MAX_TEXTURE_SIZE and falls back to the plains slot".
   - **Translucency pixel coverage.** New e2e test: the M03g ocean (camera (-284.5, 72.5, -187.5), pitch -50 degrees) batched vs the per-section path: diff 0, 62 % blue water pixels, 18 translucent submissions vs 347 total per-section submissions (local run). Screenshot `docs/screenshots/PERF-batch/perf-batch-ocean-translucent.png` shows the seabed shoreline seen through the water, deepening to dark blue.

8. **Review round 2 (queueSerial regression, tint overflow)**
   - **One fence per draw frame.** `DrawFenceTimeline` (`src/render/terrain-arena.ts`) is shared by the opaque, cutout and translucent arenas. `ChunkRenderer.render` calls `begin()` once, then `end()` after all three passes: at most one `fenceSync` per draw frame, and `begin()` polls only the oldest unsignalled fence (one pending `clientWaitSync` per frame). `allocate`, `free` and `beginUploadBatch` no longer poll; ranges freed mid-frame simply wait for the next frame's poll. An arena constructed without a timeline owns one (used by the existing unit tests). Teardown calls `timeline.releaseAll()` after the arenas.
   - **Counts per rAF frame (temporary `WebGL2RenderingContext` prototype counters in a probe spec, not committed; SwiftShader container, RD8):**

     (Settled sampled 10 s, ~14 frames; flight 124-131 frames of a 450-block flight at 30 b/s. fenceSync is above 1 per rAF because `render()` runs more than once per rAF in this harness.) The draw-data texture is already a single `texSubImage2D` of the used rows per draw frame; the remaining flight `bufferSubData` calls are chunk streaming uploads, not changed.
   - **Tint overflow.** When the atlas is at `MAX_TEXTURE_SIZE`, `getColumnTints` now returns the plains pair without calling `uploadSlotCells`, so slot 0 (atlas cells and `slotDataGrass[0]/slotDataFoliage[0]`) is never overwritten. Unit test asserts slot 0 data is unchanged after 2,100 columns.
